# 5.1 常见坑与避坑指南

> 本章适合谁：所有 FDE / 准 FDE
> 学完能掌握：12 个常见坑、避坑建议、应对方法
> 预计阅读：12 min
> 版本：v1.0 / 2026-10-13

---

## 一、技术类坑（5 个）

### 坑 1：盲目相信 Demo 效果

**场景**：
- POC 跑通、效果不错、信心满满
- 上生产环境后效果断崖式下降

**原因**：
- POC 数据与生产数据分布不同
- POC 评估标准与生产评估标准不同
- POC 没有覆盖真实业务场景

**真实案例**：
> 某零售客户 POC 阶段用精心准备的 100 条问答测试，准确率 95%。上线后发现真实用户问题多样，**准确率只有 60%**。项目紧急回滚。

**避坑**：
- POC 阶段使用真实生产数据样本（至少 1000 条）
- POC 评估与生产评估保持一致
- 上线前做灰度对比（10%、50%、100%）
- 准备"Plan B"（效果不好怎么办）

---

### 坑 2：忽视幻觉问题

**场景**：
- LLM 在生产中一本正经地胡说八道
- 客户业务受影响，投诉、退款

**真实案例**：
> 某法律 FDE 部署的合同审查 Agent 在生产中虚构了不存在的法条引用，被律师客户发现。**直接导致合同丢单、客户解约**。

**原因**：
- 没有强制 RAG
- 没有引用标注
- 没有拒答机制

**避坑**：
- 所有回答强制 RAG
- 输出带引用来源
- 设置拒答机制（置信度低时说"不知道"）
- 定期抽样审计
- 多重交叉验证（多次采样 + 一致性）

---

### 坑 3：低估集成复杂度

**场景**：
- SSO 对接用 2 周（预估 3 天）
- ERP 集成用 2 个月（预估 2 周）
- 项目严重延期

**真实案例**：
> 某政企客户 SAP R/3 系统集成，原计划 2 周，实际用 **4 个月**。其中 1 个月花在反向工程、1 个月花在数据格式不一致。

**原因**：
- 集成环境的复杂度（遗留系统）
- 合规审批链（法务、安全）
- 数据治理（数据在哪？质量如何？）

**避坑**：
- 项目计划预留 50% 缓冲
- 提前调研客户 IT 环境
- 与 IT / 法务 / 安全部门提前对齐
- 把"集成"作为核心工作而非附属工作

---

### 坑 4：没有效果评估体系

**场景**：
- 模型升级了，效果变好还是变差？不知道
- Prompt 改了，效果提升？不知道
- 客户问"AI 真的有用吗？"答不上来

**原因**：
- 没有评估数据集
- 没有评估指标
- 没有评估流程

**避坑**：
- 项目启动时同步搭建评估体系
- 定义业务指标（不仅是技术指标）
- 定期输出评估报告
- 与业务方共同定义指标

---

### 坑 5：忽视性能 / 成本

**场景**：
- 推理延迟高（用户等待 10 秒）
- Token 成本爆炸（每月烧 100 万）
- 项目不赚钱

**原因**：
- 没有压测
- 没有成本测算
- 没有性能优化

**避坑**：
- 项目早期做性能压测
- 选合适的模型（不是越大越好）
- 用缓存、批处理、量化降低 Token 成本
- 监控性能 / 成本指标

## 二、流程类坑（4 个）

### 坑 6：客户需求漂移

**场景**：
- 项目一开始是 A，做着做着变成 B，最后变成 C
- 项目严重延期，团队疲惫

**真实案例**：
> 某零售客户项目一开始是"智能客服"，做着变成"个性化推荐"，最后变成"运营自动化"。**项目延期 6 个月**，团队流失过半。

**原因**：
- 客户对自己的需求不清楚
- 客户内部政治斗争
- 没有变更管理流程

**避坑**：
- 需求阶段做充分调研
- 签订明确的需求文档
- 引入变更控制流程（需求变更需重新评估时间和成本）
- 与客户高层对齐优先级

---

### 坑 7：项目范围蔓延

**场景**：
- POC 5 个功能，签单时变 15 个，生产时要 25 个
- 项目永远做不完

**原因**：
- 没有清晰的 MVP 定义
- 没有范围控制
- 客户不断加需求

**避坑**：
- 定义 MVP（最小可行产品）
- 区分 Must / Should / Could / Won't
- 与客户明确每个阶段范围
- 用版本发布管理需求

---

### 坑 8：项目交付后没运维

**场景**：
- 项目交付后客户生产事故，没人响应
- 客户业务受损，合作中止

**原因**：
- 没有 on-call 机制
- 没有监控告警
- 没有运维文档

**避坑**：
- 交付前培训客户运维团队
- 建立 on-call 轮值
- 监控告警体系
- 编写运维手册

---

### 坑 9：经验不沉淀

**场景**：
- 一年做 5 个项目，每个项目重新摸索
- 团队成长慢、个人重复劳动

**原因**：
- 没有 Skill 库
- 没有文档沉淀机制
- 团队不分享

**避坑**：
- 每个项目结束做项目复盘
- 沉淀 Skill（案例 + 工具 + 文档）
- 团队定期分享
- 建立内部 Wiki

---

## 三、协作类坑（3 个）

### 坑 10：与客户 IT / 法务 / 安全撕逼

**场景**：
- 客户 IT 部门不配合（说"我们很忙"）
- 客户法务部门一直驳回（说"有合规风险"）
- 客户安全部门要求很多（要做等保三级）

**原因**：
- 不同部门关注点不同
- 没有共同利益
- 沟通方式不对

**避坑**：
- 当"翻译官"，把业务需求翻译成各部门语言
- 主动承担责任，不甩锅
- 找到共同利益点（"对您部门的价值是..."）
- 主动邀请各部门参与项目

---

### 坑 11：内部沟通不足

**场景**：
- 与总部产品脱节，做的方案与产品规划不一致
- 与算法团队沟通少，模型问题解决慢

**避坑**：
- 与总部产品保持定期同步
- 与算法团队建立联系
- 主动反馈客户需求
- 主动参与产品 roadmap 讨论

---

### 坑 12：客户预期管理失败

**场景**：
- 客户期望 AI 解决所有问题
- 我们交付后客户不满意
- 关系破裂

**真实案例**：
> 某制造业客户期望 AI 替代所有质检员。FDE 没有管理预期，**3 个月后客户发现 AI 只能识别 70% 缺陷**，关系紧张，最后项目失败。

**原因**：
- 售前阶段承诺过多
- 没有设置合理预期
- 没有阶段性 demo

**避坑**：
- 售前阶段保守承诺
- 阶段性 demo（每 2 周一次）
- 主动沟通进度
- 出现问题立即汇报

## 五、避坑核心原则

### 5.1 技术原则

| 原则 | 说明 |
|------|------|
| **真实数据测试** | 永远不要相信 Demo 效果 |
| **强制 RAG + 引用** | 减少幻觉 |
| **充分集成时间** | 预留 50% 缓冲 |
| **评估体系先行** | 项目启动时同步搭建 |
| **性能 / 成本监控** | 早期压测 + 持续监控 |

### 5.2 流程原则

| 原则 | 说明 |
|------|------|
| **MVP 优先** | 先做核心，再做扩展 |
| **变更管理** | 需求变更要重新评估 |
| **版本管理** | 分阶段交付 |
| **运维同步** | 交付与运维同步考虑 |
| **Skill 沉淀** | 每个项目都要沉淀 |

### 5.3 协作原则

| 原则 | 说明 |
|------|------|
| **跨部门沟通** | 主动承担沟通责任 |
| **共同利益** | 找到各方关心点 |
| **定期同步** | 与总部保持同步 |
| **预期管理** | 保守承诺、频繁 demo |

## 六、FDE 的"安全清单"

> 每个项目开始前，问自己 10 个问题：

1. 我的 POC 是否使用真实生产数据？
2. 我是否有完整的评估体系？
3. 我是否预留了集成时间？
4. 我是否定义了清晰的 MVP？
6. 我是否有变更管理流程？
6. 我是否有运维计划？
7. 我是否与客户各部门对齐了？
8. 我是否与产品 / 算法部门对齐了？
9. 我是否有监控告警体系？
10. 我是否沉淀了 Skill / 文档？

---

## 七、踩坑后的恢复方法

### 7.1 技术问题

| 问题 | 恢复方法 |
|------|---------|
| **Demo 效果不好** | 补充真实数据测试 |
| **幻觉问题** | 加强 RAG、引用、审计 |
| **集成延期** | 扩展团队、调整范围 |
| **效果不好** | 重新定义指标、A/B 测试 |
| **性能 / 成本高** | 量化、批处理、缓存 |

### 7.2 流程问题

| 问题 | 恢复方法 |
|------|---------|
| **需求漂移** | 重新对齐需求 |
| **范围蔓延** | 重新定义 MVP |
| **运维缺失** | 紧急补运维 |

### 7.3 协作问题

| 问题 | 恢复方法 |
|------|---------|
| **部门撕逼** | 升级到高层 |
| **内部脱节** | 增加同步频率 |
| **预期过高** | 主动沟通、重新对齐 |

## 八、来自老 FDE 的血泪建议

### 8.1 第一年 FDE
- "客户说的需求只是表面，要挖到真正的痛点"
- "集成真的比想象中复杂，**预留 2 倍时间**"
- "评估体系一定要先搭好，后面补很痛苦"

### 8.2 第三年 FDE
- "Skill 库是核心竞争力"
- "不要怕难，怕的是重复劳动"
- "业务结果比技术完美更重要"

### 8.3 第五年 FDE
- "行业 Know-how 是终极壁垒"
- "选对行业比选对公司更重要"
- "FDE 是创业的最佳跳板"

### 8.4 第十年 FDE
- "方法论沉淀比项目数更重要"
- "10 年 FDE 是**最难被替代**的技术人才"
- "持续学习是终身课题"

## 九、12 个坑的优先级排序

### 9.1 致命坑（会导致项目失败）
1. 盲目相信 Demo（坑 1）
2. 客户预期管理失败（坑 12）
3. 低估集成（坑 3）

### 9.2 严重坑（会导致重大损失）
1. 忽视幻觉（坑 2）
2. 没有效果评估（坑 4）
3. 客户需求漂移（坑 6）
4. 项目范围蔓延（坑 7）
5. 没有运维（坑 8）

### 9.3 一般坑（会影响效率）
1. 忽视性能 / 成本（坑 5）
2. 经验不沉淀（坑 9）
3. 跨部门撕逼（坑 10）
4. 内部沟通不足（坑 11）

## 十、避坑与个人成长

### 10.1 避坑需要的能力

- **技术深度**：识别技术坑
- **业务理解**：识别业务坑
- **沟通能力**：解决协作坑
- **流程意识**：避免流程坑
- **Ownership**：对结果负责

### 10.2 避坑是长期能力

> 避坑不是"小心谨慎"，而是**长期积累的经验**。
> 资深 FDE 之所以能避坑，是因为踩过坑。

## 十一、给不同读者的启示

### 11.1 给初级 FDE
- 不要等踩坑了才学避坑
- 项目开始前先看这 12 个坑
- 找 mentor 学习经验

### 11.2 给中级 FDE
- 把踩过的坑沉淀为 Skill
- 主动分享给团队
- 避免重复踩坑

### 11.3 给高级 FDE
- 把避坑经验沉淀为方法论
- 推动团队避坑机制
- 培养新人避坑意识

### 11.4 给公司 / 团队
- 建立避坑知识库
- 培养避坑文化
- 鼓励主动分享

## 十二、案例学习（深度避坑）

### 12.1 案例：金融项目崩盘

**问题**：
- POC 用 demo 数据，效果 95%
- 上线后生产数据效果 60%
- 客户停服、损失 200 万

**避坑**：
- POC 必须用真实数据
- 评估必须与生产一致
- 灰度上线（10%、50%、100%）

### 12.2 案例：政企项目延期

**问题**：
- 计划 2 个月，实际 6 个月
- 集成用了一半时间
- 团队疲惫

**避坑**：
- 集成预留 50% 缓冲
- 提前调研 IT 环境
- 与各部门提前对齐

### 12.3 案例：零售项目翻车

**问题**：
- 客户期望 AI 替代所有客服
- 实际只能解决 70%
- 客户不满

**避坑**：
- 售前保守承诺
- 阶段性 demo
- 主动沟通
