## 一、20/80 法则

很多人以为 FDE = 写 demo，**实际上集成墙（Integration Wall）才是主战场**：

| 占比 | 工作内容 |
|------|---------|
| **20%** | Demo 跑通，模型效果看起来不错 |
| **80%** | SSO 对接、遗留 ETL、合规审查、安全团队审批、数据脱敏、权限矩阵、生产事故… |

这个 20/80 法则几乎是行业铁律：
- 算法工程师容易低估 80% 的工作量
- 新人 FDE 容易栽在"没想到这么复杂"
- 资深 FDE 都从"集成墙"里爬出来过

## 二、集成墙的 4 大组成

### 2.1 客户 IT 环境的复杂度

**常见场景**：
- 10 年前的 ERP（SAP R/3、Oracle EBS）没人维护
- 中间件版本各异（WebLogic、JBoss、Tuxedo）
- 数据库 schema 混乱（一个表 200 列）
- 自研系统无文档

**典型难度**：
- 与 SAP 集成：要走 RFC / BAPI，可能要研究几个月
- 与自研系统对接：要从日志反推协议
- 与老旧数据库交互：字段含义只有老员工知道

### 2.2 合规审批链

**常见流程**：
```
业务部门申请 → IT 部门评估 → 安全团队审查 → 法务部门审核 → 数据部门评估 → 高管批准
```

**典型时长**：
- 简单项目：1-2 周
- 政企项目：1-3 个月
- 涉密项目：3-6 个月

**典型挑战**：
- 每个部门关注点不同
- 一个部门卡住整个项目
- 客户内部政治斗争

### 2.3 数据治理

**三大问题**：
1. **数据在哪**：分散在 20 个数据库、5 个文件系统
2. **质量如何**：字段缺失、格式混乱、定义不清
3. **能不能用**：敏感数据、客户隐私、商业秘密

**典型工作**：
- 数据源调研（2-4 周）
- 数据清洗（2-6 周）
- 数据脱敏（1-2 周）
- 数据同步管道建设（2-4 周）

### 2.4 效果评估

**三大挑战**：
1. **怎么证明 AI 比原来好？**
   - 没有对照组
   - 业务指标难量化
   - 客户预期过高

2. **评估指标谁来定？**
   - 技术指标容易（准确率、延迟）
   - 业务指标难（转化率、效率）

3. **评估数据从哪来？**
   - 历史数据缺失
   - 标注成本高
   - 评估频率难定

## 三、FDE 的 80% 时间花在哪些事

### 3.1 系统对接（约 40% 时间）

#### 3.1.1 SSO 集成
**典型工作**：
- 调研客户 SSO 方案（OIDC / SAML / LDAP）
- 配置 IdP（Okta、Azure AD、自研）
- 集成 Token 流程
- 用户组映射、角色映射
- 测试各种边界情况

**典型耗时**：2-6 周

#### 3.1.2 ETL（数据抽取-转换-加载）
**典型工作**：
- 调研数据源（MySQL、PostgreSQL、Oracle、MongoDB）
- 设计 ETL pipeline（Airflow、Flink）
- 数据清洗、转换、脱敏
- 增量同步、断点续传
- 监控告警

**典型耗时**：4-12 周

#### 3.1.3 API 集成
**典型工作**：
- 调研 API（REST / GraphQL / gRPC）
- 处理鉴权（API Key、OAuth、JWT）
- 处理错误码（重试、降级）
- 处理限流
- 编写 SDK

**典型耗时**：2-8 周

#### 3.1.4 消息队列
**典型工作**：
- 选型（Kafka、RocketMQ、RabbitMQ）
- 部署集群
- 编写生产 / 消费
- 死信处理
- 监控告警

**典型耗时**：2-4 周

#### 3.1.5 遗留系统
**典型工作**：
- 反向工程（读代码、读日志）
- 适配层编写
- 异常处理
- 长期维护

**典型耗时**：4-12 周

### 3.2 部署运维（约 20% 时间）

#### 3.2.1 容器化
**典型工作**：
- Dockerfile 编写
- 多阶段构建
- 镜像优化
- 镜像仓库管理

#### 3.2.2 编排
**典型工作**：
- K8s 资源清单（Deployment、Service、ConfigMap、Secret）
- Helm Chart 编写
- Ingress、NetworkPolicy
- HPA（自动伸缩）

#### 3.2.3 CI/CD
**典型工作**：
- Pipeline 编写
- 自动化测试
- 灰度发布
- 回滚机制

#### 3.2.4 监控
**典型工作**：
- Prometheus + Grafana
- 日志收集（ELK / EFK）
- Trace（Jaeger / Zipkin）
- 告警规则

### 3.3 合规安全（约 10% 时间）

#### 3.3.1 数据安全
- 数据脱敏（替换 / 掩码 / 加密）
- 加密传输（HTTPS、TLS）
- 加密存储（AES、国密）
- 权限模型（RBAC、ABAC）

#### 3.3.2 合规框架
- 等保（中国）
- GDPR（欧盟）
- SOC 2（美国）
- HIPAA（医疗）
- ISO 27001

#### 3.3.3 安全审计
- 漏洞扫描
- 渗透测试
- 安全加固

### 3.4 沟通协调（约 10% 时间）
- 与客户 IT 团队对接
- 与法务 / 安全团队沟通
- 与业务方确认需求

## 四、典型"隐形工作"场景详解

### 4.1 场景一：SSO 集成

**背景**：客户用 Azure AD，要求所有内部系统接入 SSO

**FDE 的工作**：
1. **第 1-2 天**：调研 Azure AD 配置、Token 流程
2. **第 3-5 天**：搭建测试环境（dev tenant）
3. **第 6-10 天**：编写 OIDC 集成代码
4. **第 11-14 天**：测试各种场景（登录、登出、Token 刷新）
5. **第 15-20 天**：与客户 IT 团队联调
6. **第 21-25 天**：权限映射、用户组同步
8. **第 26-30 天**：上线、运维文档

**可能踩的坑**：
- Token 过期处理
- Refresh Token 安全
- 跨域 SSO
- 移动端 SSO
- 异常处理（IdP 不可用）

### 4.2 场景二：遗留 ERP 对接

**背景**：客户用 SAP R/3（30 年前系统），需要把工单数据同步到 AI 系统

**FDE 的工作**：
1. **第 1-2 周**：调研 SAP 系统（RFC、BAPI、IDoc）
2. **第 3-4 周**：搭建 SAP 连接器（用 PyRFC 或 SAP JCo）
3. **第 5-6 周**：编写数据同步 pipeline
4. **第 7-8 周**：测试异常处理（连接断开、数据格式异常）
5. **第 9-10 周**：上线、运维

**难点**：
- SAP 接口复杂，文档不全
- 性能问题（SAP 慢查询）
- 字段映射（语义理解）
- 错误处理（重试 vs 报警）

### 4.3 场景三：等保三级合规

**背景**：政企客户要求等保三级

**FDE 的工作**：
1. **调研等保要求**（3-5 天）
2. **差距分析**（3-5 天）
3. **整改方案**（1 周）
4. **安全加固**（密码策略、访问控制、审计日志）（2-4 周）
5. **安全测试**（渗透测试、漏洞扫描）（1-2 周）
6. **协助客户完成等保测评**（2-4 周）

**整改清单示例**：
- 密码策略（长度、复杂度、过期时间）
- 访问控制（最小权限原则）
- 审计日志（操作日志、错误日志）
- 数据加密（传输加密、存储加密）
- 漏洞管理（定期扫描、及时修复）

### 4.4 场景四：数据脱敏

**背景**：客户敏感数据不能出域（个人隐私、商业机密）

**FDE 的工作**：
1. **数据分级**（识别敏感数据：姓名、身份证、手机号）
2. **脱敏策略**（替换、掩码、加密）
3. **脱敏算法**（保持分布、可关联）
5. **测试**（验证 AI 效果不下降）
6. **运维**（脱敏规则的更新维护）

**难点**：
- 脱敏不能影响 AI 效果
- 不同数据类型不同策略
- 性能开销（脱敏耗时）

### 4.5 场景五：评估体系搭建

**背景**：怎么证明 AI 比原来好？

**FDE 的工作**：
1. **定义评估指标**（技术 + 业务）
2. **收集评估数据**（历史对话、人工标注）
3. **搭建评估 pipeline**（自动化评估）
4. **与业务方对齐**（评估结果可视化）
5. **持续迭代**（指标更新、模型升级）

## 六、隐形工作的应对方法

### 6.1 沉淀 Skill 库（最有效 ⭐⭐⭐）

> 详见 [5.2-未来趋势（2026+）](../模块五-未来与避坑/5.2-未来趋势（2026+）.md)

**核心方法**：
- 把重复出现的问题沉淀为 Skill
- 下个项目直接调用 Skill
- 团队共享 Skill 库

**Skill 示例**：
- "Azure AD OIDC 集成"
- "SAP RFC 数据同步"
- "等保三级整改清单"
- "金融数据脱敏模板"

### 6.2 建立行业 Know-how

**方法**：
- 深入了解 1-2 个行业
- 知道常见 IT 架构、合规要求
- 见客户前能预判难点

**好处**：
- 项目规划更准确
- 与客户沟通更专业
- 出问题能快速定位

### 6.3 培养系统集成能力

**核心技能**：
- SSO / OAuth / SAML
- ETL（Airflow / dbt / Flink）
- API（REST / GraphQL / gRPC）
- 消息队列（Kafka / RocketMQ）
- 遗留系统适配

### 6.4 拥抱"脏活"

**心态调整**：
- 不要怕 SSO 对接、合规审查
- 这些才是 FDE 的护城河
- 算法工程师做不了这些

## 七、FDE 与"纯算法工程师"的核心区别

| 维度 | 纯算法工程师 | FDE |
|------|------------|-----|
| 核心战场 | 模型优化 | 系统集成 |
| 难点 | 数学 / 训练 | 兼容性 / 合规 |
| 成就感来源 | 论文 / benchmark | 客户业务跑通 |
| 失败原因 | 模型效果不好 | 集成失败 / 合规不过 |
| 替代性 | 容易被 AutoML 替代 | 短期难以被替代 |
| 薪资上限 | 100+ 万 | 100+ 万 |
| 工作节奏 | 安静 / 研究 | 高压 / 交付 |

## 九、为什么 FDE 薪资高

FDE 薪资高的本质原因是**稀缺性**：

### 9.1 稀缺性分析

**需要的能力组合**：
- 懂 LLM（AI 时代的核心技能）
- 懂集成（系统集成的硬技能）
- 懂客户（业务理解 + 沟通能力）

**三者兼具的人才极少**：
- 算法工程师：缺乏集成 + 客户能力
- 后端工程师：缺乏 LLM + 客户能力
- 售前工程师：缺乏 LLM + 集成能力

### 9.2 不可替代性

- 算法可以被 AutoML 替代
- 但**集成 / 合规 / 业务理解短期难被替代**
- 这就是 FDE 的护城河

### 9.3 业务价值

- FDE 直接对客户业务结果负责
- 业务成功 = 客户续约 = 厂商收入

### 9.4 辛苦溢价

- 出差、驻场、on-call
- 高强度、高压力
- 溢价合理

## 十、隐形工作清单（自检表）

> 项目启动前，问自己这些问题：

- [ ] 客户的 IT 架构是什么？
- [ ] 客户的 SSO 方案是什么？
- [ ] 客户的数据库在哪儿、怎么访问？
- [ ] 客户的合规要求是什么（等保、GDPR、行业法规）？
- [ ] 客户的数据治理现状如何？
- [ ] 客户的安全团队要求如何（审计、漏洞扫描）？
- [ ] 客户的法务流程对 ICT 有多长？
- [ ] 客户的运维要求是什么（on-call、SLA）？
- [ ] 客户的故障应急流程是什么？
- [ ] 客户的业务高峰期是什么时候？
- [ ] 我有没有应对所有这些的 Skill？

## 十一、给不同读者的启示

### 11.1 给新人 FDE
- 不要被"集成墙"吓到，这是常态
- 多向资深 FDE 学习他们的 Skill 库
- 主动记录"重复场景"，形成自己的工具箱

### 11.2 给资深 FDE
- 把自己的经验沉淀为 Skill
- 主动分享给团队
- 推动团队建立 Skill 库

### 11.3 给公司 / 团队
- 建立 FDE Skill 库
- 鼓励跨项目复用
- 把 FDE 的"脏活"系统化
