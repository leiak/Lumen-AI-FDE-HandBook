## 案例一：金融客户智能风控 Agent

### 1.1 客户背景

- **行业**：股份制商业银行
- **场景**：信用卡反欺诈
- **痛点**：传统规则引擎漏判率高，人工审核压力大

### 1.2 项目目标

- 构建基于大模型的风控 Agent
- 提升欺诈识别准确率
- 降低人工审核工作量

### 1.3 技术方案

**整体架构**：
```
交易事件 → 实时特征计算 → RAG 检索历史案例 → Agent 推理 → 决策
                                ↓
                         风控知识库（历史欺诈案例 + 监管规则）
                                ↓
                         决策结果（拦截 / 人工审核 / 通过）
```

**关键技术**：
- 实时特征计算（Flink）
- RAG 检索（pgvector）
- Agent 推理（LangGraph + Claude）
- 模型评估（A/B 测试）

**关键技术细节**：

#### 1.3.1 实时特征计算
- **技术**：Flink + Kafka
- **特征**：交易金额、时间、地点、设备、历史行为
- **延迟**：<100ms

#### 1.3.2 RAG 检索历史案例
- **向量库**：pgvector（已用 PostgreSQL）
- **文档**：过去 3 年的欺诈案例
- **检索**：相似案例 + 监管规则

#### 1.3.3 Agent 推理
- **框架**：LangGraph
- **模型**：Claude（私有化部署）
- **决策**：拦截 / 人工审核 / 通过

#### 1.3.4 模型评估
- **方法**：A/B 测试 + 离线评估
- **指标**：准确率、召回率、人工审核率

### 1.4 关键挑战

#### 挑战 1：数据不出域
- **解决**：私有化部署在客户内网
- **实施**：所有数据、模型、推理都在内网

#### 挑战 2：监管合规
- **要求**：所有决策可追溯
- **解决**：完整的审计日志、决策依据记录

#### 挑战 3：效果评估
- **难点**：不能直接上线，必须有对照组
- **解决**：A/B 测试、离线评估、专家评审

### 1.5 业务结果

| 指标 | 上线前 | 上线后 | 变化 |
|------|--------|--------|------|
| 欺诈识别准确率 | 65% | 85% | **+20%** |
| 人工审核工作量 | 100% | 60% | **-40%** |
| 误判率 | 10% | 5% | **-50%** |
| 客户满意度 | 3.5/5 | 4.5/5 | **+1.0** |
| 续约 | - | +3 年 | **续约** |

### 1.6 经验沉淀

#### Skill
- **金融风控 Agent 模板**：可直接复用
- **实时 RAG 评估脚本**：自动化评估
- **金融合规清单**：等保、银保监要求

#### 文档
- **项目方案**：完整架构、决策记录
- **运维手册**：故障排查、应急响应
- **复盘报告**：经验教训

## 案例二：零售客户智能客服 RAG

### 2.1 客户背景

- **行业**：头部电商平台
- **场景**：售前售后客服
- **痛点**：人工客服成本高、响应慢、知识更新不及时

### 2.2 项目目标

- 搭建基于知识库的智能客服
- 7×24 自动响应
- 降低人工客服成本

### 2.3 技术方案

**整体架构**：
```
用户提问 → 意图识别 → 商品知识库 RAG → 答案生成 → 多轮对话
                ↓                       ↓
            工单系统              FAQ 知识库
                                      ↓
                              自动转人工（置信度低时）
```

**关键技术**：

#### 2.3.1 意图识别
- **技术**：BERT + 规则
- **意图**：商品咨询、物流查询、退换货、投诉等
- **准确率**：95%

#### 2.3.2 RAG 检索
- **向量库**：Milvus
- **文档**：商品库、FAQ、政策文档
- **检索**：向量 + BM25 混合检索

#### 2.3.3 多轮对话管理
- **框架**：自研 + LangChain
- **状态**：对话状态、上下文管理
- **多轮**：5-10 轮对话

#### 2.3.4 自动转人工
- **触发条件**：置信度 < 0.6、用户主动请求
- **流程**：无缝转人工、保留上下文

### 2.4 关键挑战

#### 挑战 1：大促备战（双 11、618）
- **难点**：流量 10 倍
- **解决**：
  - 提前 1 个月压测演练
  - 自动扩缩容（HPA）
  - 降级方案（关闭非核心功能）

#### 挑战 2：知识更新
- **难点**：每天有新商品上架
- **解决**：
  - 自动化知识更新 pipeline
  - 每天凌晨全量更新
  - 紧急更新（30 分钟内生效）

#### 挑战 3：多轮对话
- **难点**：用户经常中途改变话题
- **解决**：
  - Context Engineering
  - 多轮上下文管理
  - 意图动态调整

### 2.5 业务结果

| 指标 | 上线前 | 上线后 | 变化 |
|------|--------|--------|------|
| 自动解决率 | 0% | 70% | **+70%** |
| 人工客服成本 | 100% | 65% | **-35%** |
| 大促承接流量 | - | 80% | - |
| 平均响应时间 | 30s | 2s | **-93%** |
| NPS | 3.8/5 | 4.4/5 | **+0.6** |

### 2.6 经验沉淀

#### Skill
- **电商客服 RAG 模板**：可复用
- **大促备战手册**：从压测到应急
- **知识更新 pipeline**：自动化

#### 工具
- **意图识别模型**：自研
- **多轮对话框架**：自研 + LangChain
- **降级开关**：快速响应

## 案例三：政企客户政务问答系统

### 3.1 客户背景

- **行业**：某市政府
- **场景**：政务问答、政策咨询
- **痛点**：市民咨询量大、电话接通率低

### 3.2 项目目标

- 搭建政务问答系统
- 支持政策法规查询、办事指南
- 提升市民服务体验

### 3.3 技术方案

**整体架构**：
```
市民提问 → 政务知识库 RAG → 答案生成（含出处）
              ↓
        政策法规库
        办事指南库
        常见问题库
              ↓
        安全审核（敏感词、政治合规）
              ↓
        最终答案
```

**关键技术**：

#### 3.3.1 信创全栈适配
- **CPU**：华为鲲鹏
- **操作系统**：麒麟
- **数据库**：达梦 DB
- **大模型**：盘古大模型
- **中间件**：东方通

#### 3.3.2 政务知识库
- **文档**：政策法规、办事指南、常见问题
- **格式**：PDF（扫描件 + 电子件）、Word、HTML
- **解析**：OCR + 版式识别 + 表格识别

#### 3.3.3 安全审核
- **敏感词过滤**：政治敏感词库
- **合规审查**：所有回答必须可追溯
- **审计日志**：完整记录

#### 3.3.4 私有化部署
- **网络**：内网隔离
- **安全**：等保三级
- **数据**：不出域

### 3.4 关键挑战

#### 挑战 1：信创适配
- **难点**：所有组件必须国产化
- **解决**：
  - 与华为深度合作
  - 自研适配层
  - 性能优化（信创硬件性能较弱）

#### 挑战 2：数据合规
- **要求**：不能联网
- **解决**：
  - 离线部署
  - 离线知识更新（U盘导入）
  - 严格的访问控制

#### 挑战 3：政治正确
- **要求**：所有回答必须审核
- **解决**：
  - 敏感词过滤
  - 引用必须来自权威来源
  - 拒答机制（不确定就不答）

### 3.5 业务结果

| 指标 | 上线前 | 上线后 | 变化 |
|------|--------|--------|------|
| 政务问答准确率 | - | 90% | - |
| 市民电话咨询量 | 100% | 70% | **-30%** |
| 24h 服务能力 | ❌ | ✅ | - |
| 政策更新及时性 | - | T+1 | - |

### 3.6 经验沉淀

#### Skill
- **政务知识库构建**：从 PDF 解析到入库
- **自研适配层**：信创适配
- **政治合规清单**：敏感词、引用规范

#### 文档
- **信创适配清单**：从硬件到中间件
- **政务合规检查**：等保三级
- **应急响应**：政治风险处理

## 案例四：制造客户设备预测性维护

### 4.1 客户背景

- **行业**：汽车制造
- **场景**：生产设备故障预测
- **痛点**：设备故障导致停产损失大

### 4.2 项目目标

- 基于传感器数据预测设备故障
- 提前预警、减少停产
- 降低维护成本

### 4.3 技术方案

**整体架构**：
```
传感器数据 → 时序数据库 → 异常检测 → Agent 决策
                                      ↓
                            维修知识库 RAG
                                      ↓
                            维修建议 + 工单
```

**关键技术**：

#### 4.3.1 时序数据接入
- **数据库**：InfluxDB
- **采集**：OPC UA、Modbus 协议
- **频率**：每分钟采集

#### 4.3.2 异常检测
- **方法**：统计异常 + ML 异常
- **延迟**：<5 分钟
- **覆盖**：100+ 台关键设备

#### 4.3.3 维修知识库 RAG
- **向量库**：pgvector
- **文档**：维修手册、故障案例、老师傅经验
- **检索**：故障现象 → 维修方案

#### 4.3.4 工单系统集成
- **系统**：SAP PM
- **集成**：API + 消息队列
- **流程**：检测到异常 → 自动生成工单

### 4.4 关键挑战

#### 挑战 1：数据接入
- **难点**：与 MES / ERP 集成
- **解决**：
  - 标准协议（OPC UA）
  - 自研适配器（Modbus）
  - 边缘计算（部分场景）

#### 挑战 2：误报控制
- **难点**：误报会导致维修人员疲劳
- **解决**：
  - 多维度检测（统计 + ML）
  - 人工审核（高风险告警）
  - 持续优化模型

#### 挑战 3：边缘计算
- **需求**：部分场景需本地推理
- **解决**：
  - 边缘设备（NVIDIA Jetson）
  - 模型量化（INT8）
  - 云边协同

### 4.5 业务结果

| 指标 | 上线前 | 上线后 | 变化 |
|------|--------|--------|------|
| 设备故障预测准确率 | - | 75% | - |
| 停产时间 | 100% | 50% | **-50%** |
| 维修成本 | 100% | 80% | **-20%** |
| 计划外停机次数 | 100% | 60% | **-40%** |

### 4.6 经验沉淀

#### Skill
- **设备预测模板**：时序数据 + ML + Agent
- **时序数据接入脚本**：OPC UA、Modbus
- **MES 集成手册**：常见系统对接

## 案例五：法律客户合同审查 Agent

### 5.1 客户背景

- **行业**：头部律所
- **场景**：合同审查、法律研究
- **痛点**：律师效率低、文档量大

### 5.2 项目目标

- 搭建合同审查 Agent
- 自动识别风险条款
- 提升律师效率

### 5.3 技术方案

**整体架构**：
```
合同文档 → 文档解析 → 条款抽取 → 风险识别 → 审查报告
              ↓             ↓
        PDF/Word      法律知识库 RAG
        OCR（扫描件）   监管规则库
        版式识别
```

**关键技术**：

#### 5.3.1 长上下文模型
- **模型**：Kimi（200K 上下文）
- **优势**：合同常常 100+ 页
- **优化**：KV Cache、Prefix Caching

#### 5.3.2 文档解析
- **PDF**：PyMuPDF + 版式识别
- **扫描件**：PaddleOCR
- **表格**：Table Transformer

#### 5.3.3 条款抽取
- **NER**：法条、案件、人物、金额
- **分类**：合同类型、风险类型
- **关系**：条款关联

#### 5.3.4 GraphRAG
- **图谱**：法条关联、案件引用
- **检索**：实体 → 关联 → 检索
- **优势**：法律知识是网状结构

### 5.4 关键挑战

#### 挑战 1：长文档
- **难点**：合同常常 100 页+
- **解决**：
  - 长上下文模型（Kimi）
  - 文档分层处理
  - 关键条款优先

#### 挑战 2：准确性
- **难点**：法律不能出错
- **解决**：
  - 多次采样 + 一致性
  - 人工审核（高风险条款）
  - 严格引用来源

#### 挑战 3：可解释性
- **要求**：必须解释依据
- **解决**：
  - GraphRAG 给出关联法条
  - 详细引用来源
  - 审查报告包含法律依据

### 5.5 业务结果

| 指标 | 上线前 | 上线后 | 变化 |
|------|--------|--------|------|
| 合同审查时间 | 4 小时 | 30 分钟 | **-87%** |
| 风险识别准确率 | - | 85% | - |
| 律师人均产能 | 1x | 2x | **+100%** |
| 客户满意度 | 3.8/5 | 4.6/5 | **+0.8** |

### 5.6 经验沉淀

#### Skill
- **合同审查模板**：可复用
- **法律文档解析 pipeline**：PDF/扫描件
- **法律 RAG 评估标准**：准确性、可解释性

## 六、5 大案例共性提炼

### 6.1 通用流程

```
客户需求 → 业务诊断 → POC 验证 → 系统集成 → 私有化部署 → 运维迭代
```

### 6.2 常见难点

| 难点 | 描述 |
|------|------|
| **数据** | 数据在哪？质量如何？能不能用？|
| **合规** | 等保、GDPR、HIPAA 等 |
| **集成** | SSO、ERP、MES、遗留系统 |

- **客户业务必须真的受益** | 不是"功能上线"

- **可持续的运营** | 不是一次性项目

### 6.4 FDE 价值体现

- **客户 Insight**：理解客户业务
- **技术深度**：解决真问题
- **交付能力**：按时按质
- **反哺产品**：沉淀 Skill、文档

## 九、典型反面案例（避坑学习）

### 9.1 反面案例 A：POC 效果很好，生产崩盘

**问题**：
- POC 用的是精心准备的 demo 数据
- 生产数据分布完全不同
- 准确率从 95% 降到 60%

**教训**：
- POC 必须用真实数据
- 评估指标必须与生产一致

### 9.2 反面案例 B：忽视集成墙

**问题**：
- 计划 2 周集成，实际用了 3 个月
- SSO、ETL、合规都没预估到

**教训**：
- 集成预留 50% 缓冲
- 提前调研客户 IT 环境

### 9.3 反面案例 C：忽视合规

**问题**：
- 上线前没做等保测评
- 被迫停服 2 周整改

**教训**：
- 合规前置
- 项目早期就预评估

### 9.4 反面案例 D：评估体系缺失

**问题**：
- 模型升级后效果变差，无人发现
- 客户投诉才知道

**教训**：
- 评估体系先行
- 持续监控告警
